## Highest priority

1. **A trial owner can schedule every branch for removal.** With two active branches and no subscription, scheduling the first branch makes it read-only. The guard for removing the second still counts the first as a surviving branch. The removal writer calculates a target of zero, and the deadline job can archive both because neither removal has a linked subscription. The documented minimum is one. A regression test should schedule the two removals in sequence and check that the second is rejected. *Source trace.* [Two-branch trial setup](../../tests/integration/services/branch-billing-lifecycle.test.ts#L303) · [Minimum-branch rule](../domain-invariants.md#L269) · [Guard and target calculation](../../services/branch.service.ts#L944) · [Archival](../../services/branch.service.ts#L1112)

2. **The first paid mandate can include a branch that leaves at trial end.** Schedule one of two trial branches for removal, then authorize the first subscription before the trial ends. Checkout counts both nonarchived branches and sends quantity two for the first paid period. The earlier removal has no subscription ID. Its deadline path can archive the branch without reconciling that mandate to one. This establishes the incorrect quantity requested from the provider. A live charge was outside the review. *Source trace.* [Removal record](../../services/branch.service.ts#L971) · [Checkout count](../../services/billing.service.ts#L2039) · [Provider request](../../services/billing.service.ts#L2331) · [Deadline filter](../../services/billingDeadline.service.ts#L325)

3. **An Excel joining date can silently change the student's billing anniversary.** An in-memory workbook contained a native date of **4 November 2026**, displayed with the Excel format `m/d/yyyy`. The workbook parser produced `11/4/2026`. The date normalizer accepted that value as **11 April 2026**. Both dates are valid, so the date validation supplies no warning. Preserve the native calendar date when reading date-typed cells and test US- and Indian-formatted views of the same cell. *Reproduced.* [Workbook cell conversion](../../importing/parsers/xlsx.parser.ts#L128) · [Date interpretation](../../importing/utils/row-normalizer.ts#L41) · [Joining-date assignment](../../importing/utils/row-normalizer.ts#L112) · [Fee-cycle anchor](../../utils/studentBillingCycles.ts#L14)

## Fees, billing and imports

4. **A contradictory payment legend can be confirmed as paid.** The import editor submits paid, unpaid and waived value lists independently. The request parser accepted `X` under paid and `x` under unpaid. The classifier compares case-insensitively and returned `PAID` for `x`. An eligible row can therefore enter a reviewed plan with a definite payment status despite the conflicting instructions. Validate that the confirmed lists are disjoint after normalization. *Reproduced.* [Editor](../../app/branch/%5BbranchId%5D/onboarding/import/%5BsessionId%5D/_components/PaymentsStep.tsx#L166) · [Request parser](../../importing/http/import-mapping-request.ts#L149) · [Classifier](../../importing/utils/row-normalizer.ts#L85)

5. **Basic and Pro trial checkout can quote a full plan fee due today.** During first authorization, the overview calculates zero for every active trial. The confirmation dialog's amount checks specifically for Standard trial and can display the monthly total for Basic or Pro. The provider request schedules the plan charge for trial end. This is a discrepancy in the amount presented for consent. *Source trace.* [Overview](../../services/billingExperience.service.ts#L300) · [Confirmation amount](../../components/billing/OrganizationBillingContent.tsx#L900) · [Rendered amount](../../components/billing/CheckoutConfirmationDialog.tsx#L107) · [First charge date](../../services/billing.service.ts#L2263)

6. **Generation can add debt after a student's deactivation and settlement.** The daily generator reads active students and stages dues before a later batch insert. Deactivation can commit between those operations and settle every due it sees. The batch can then insert the staged due for the now-inactive student. The write needs to recheck eligibility under the same student lock as settlement. *Source trace of a concurrent execution.* [Eligibility read](../../services/payment.service.ts#L195) · [Batch insert](../../services/payment.service.ts#L159) · [Deactivation settlement](../../services/student.service.ts#L755) · [Required behavior](../domain-invariants.md#L318)

7. **A student with a ₹0 monthly fee can become overdue.** Zero is a valid fee. Generation creates a monthly `DUE` row for that amount. The renewals logic categorized a zero-balance example as both outstanding and overdue, while the collection picker excludes it. The office can chase a student who owes nothing. *Classification reproduced, generation and picker traced.* [Generator](../../services/payment.service.ts#L220) · [Renewals queue](../../services/renewals.service.ts#L63) · [Categories](../../lib/renewals.ts#L68) · [Collectible balances](../../services/feeCollection.service.ts#L105)

8. **Deactivation describes an unreadable balance as a clean financial record.** Staff with student access and without payment-view permission see “No payment access” in the roster. Opening deactivation passes an empty payments array to the dialog, which says “No outstanding payments” even for a student with debt. Preserve an unavailable state through the confirmation dialog. *Source trace.* [Payment loading](../../app/branch/%5BbranchId%5D/students/page.tsx#L469) · [Roster](../../app/branch/%5BbranchId%5D/students/page.tsx#L691) · [Dialog data](../../app/branch/%5BbranchId%5D/students/page.tsx#L1059) · [Displayed claim](../../app/branch/%5BbranchId%5D/students/page.tsx#L322)

9. **An unfinished collection can follow the next cashier using the same tab.** The full-workspace dialog restores a pending request using branch and student IDs alone. After an account switch, a second authorized cashier opening that student's dialog can inherit the first cashier's amount, reference and note. If the first submission never committed, explicitly retrying it records the second cashier as the actor. The dedicated receipt-recovery read already checks the actor. *Source trace.* [Draft key and restoration](../../components/payments/CollectFeeDialog.tsx#L41) · [Retry](../../components/payments/CollectFeeDialog.tsx#L74) · [Actor attribution](../../services/feeCollection.service.ts#L58) · [Recovery scope](../../services/feeCollection.service.ts#L99)

## Analytics and AI reports

10. **November's collection rate can show 200% in Branch Analytics and 0% on the dashboard.** In the fixture, the branch collected ₹1,000 against an October bill during November. November's ₹500 bill remained unpaid. Analytics divided November cash by fees due in November. The dashboard measured settlement of the fees actually due in November. Both display “Collection rate.” Use the same fee cohort for that label and display calendar cash as its own amount. *Reproduced.* [Analytics arithmetic](../../analytics/payment.analytics.ts#L152) · [Analytics label](../../components/snapshot/SideStats.tsx#L16) · [Dashboard arithmetic](../../services/dashboard.service.ts#L177)

11. **Older imported payments can inflate “Collected this month.”** The dashboard includes any non-ledger paid fee whose stored payment date falls in the month. Financial Analytics excludes rows with an import-resolution event. The financial reporting rule explicitly excludes imported resolutions from dated collections. This affects historical imported rows that retained a payment date. *Source trace.* [Dashboard sum](../../services/dashboard.service.ts#L163) · [Analytics exclusion](../../analytics/payment.analytics.ts#L135) · [Reporting rule](../ai/fee-collections.md#L49)

12. **The first point in a monthly chart can contain the previous month's fees.** An India browser sent 1 November midnight as 31 October at 18:30 UTC. On a UTC server the first point used October for its month-to-date calculation. With ₹1,000 billed only in October, the chart showed ₹1,000 on 1 November and ₹0 on 2 November. Use one business timezone for range creation, bucketing and labels. *Reproduced using India and UTC clocks.* [Browser range](../../lib/analyticsPageLoader.ts#L21) · [Daily trend](../../analytics/trends/payment.trends.ts#L32) · [Server month](../../analytics/payment.analytics.ts#L114)

13. **AI Reports can say 300% of students have overdue fees.** Three overdue fee rows for one active student produced “300.0% of students have overdue payments” and a critical health score. The numerator counts fees and the denominator counts people. Count distinct overdue students from the same eligible population before applying the risk threshold. *Reproduced.* [Fee count](../../analytics/payment.analytics.ts#L85) · [Risk calculation and wording](../../ai/riskDetection/branchRiskDetector.ts#L19)

14. **The same healthy branch can receive different risk badges and action lists as model availability changes.** A paid-up, fully occupied branch with zero inactive students received a critical financial badge from a validly shaped model response. With the model unavailable, it received a low financial badge and an action to re-engage inactive students. The overall health score stayed healthy. The documented contract makes risks and actions deterministic. *Reproduced with a stubbed provider.* [Contract](../domain-invariants.md#L1191) · [Fallback actions](../../ai/branchHealthReport.ts#L93) · [Model-supplied risk](../../ai/branchHealthReport.ts#L116)

15. **Adding seats or a shift can leave today's AI capacity report stale.** Single-seat, batch-seat and shift creation change capacity without advancing the branch's data-change timestamp. The report cache uses that timestamp to reuse today's report. Adding ten seats after report generation can therefore leave the old capacity on screen for the rest of the day when no other update refreshes the timestamp. *Source trace.* [Single seat](../../services/seat.service.ts#L152) · [Batch seats](../../services/seat.service.ts#L186) · [New shift](../../services/shift.service.ts#L127) · [Cache decision](../../ai/orchestrator/branchAI.orchestrator.ts#L146)

## Seating, attendance and renewals

16. **A noon seat move can occupy two seats in the 9 a.m. snapshot.** One student moved from A to B in a two-seat shift. The historical occupancy query admitted allocations starting any time that day and retained old allocations ending after 9 a.m. It counted both and returned 100% utilization instead of 50%. Apply the same instant to both ends of each allocation. *Reproduced with a fixture that applied the query filters.* [Allocation bounds](../../services/seat.service.ts#L288) · [Occupancy count](../../services/seat.service.ts#L329) · [Trend caller](../../analytics/trends/seat.trends.ts#L21)

17. **Shift deletion can preselect a bulk move that the service must reject.** A student holds separate morning and evening assignments. The evening shift has another free seat. Deleting morning offers evening as a target based on spare capacity alone, although the writer rejects moving the same student into evening twice. This fails even if nobody edits the branch between preview and confirmation. *Source trace.* [Preview calculation](../../services/shift.service.ts#L270) · [Default selection](../../app/branch/%5BbranchId%5D/shifts/page.tsx#L466) · [Write check](../../services/shift.service.ts#L371)

18. **An added renewal can inherit a previously dismissed notification.** Dismiss an alert for three expiring memberships, then add a fourth expiring later in the same week. The total becomes four, but the notification identity uses only the first three terms. Its dismissed state carried forward in the fixture. The fourth term remains visible in the worklist while its updated alert stays hidden. *Reproduced.* [Three-term sample](../../services/dashboard.service.ts#L205) · [Notification identity](../../services/dashboard.service.ts#L537) · [Bell filter](../../components/layout/BranchNotifications.tsx#L56)

19. **The attendance export includes some unmarked students despite saying it excludes them.** Clearing a mark persists a `NOT_MARKED` row. The all-status export returns it. A student whose mark was never entered has the same visible attendance status and is absent from the export. *Source trace.* [Clear operation](../../services/attendance.service.ts#L82) · [Report query](../../services/branchReport.service.ts#L61) · [Export description](../../components/dashboard-features/ReportsContent.tsx#L121)

## Search, settings and operational status

20. **Searching for a student can miss their assigned seat.** On a seat shared across shifts, the database query matches any current occupant's name, then returns just one occupant without requiring that person to match. If it returns the morning occupant for an evening student's name, the result scorer drops the seat. *Result filtering reproduced, query traced.* [Seat lookup](../../services/branchSearch.service.ts#L135) · [Single-occupant selection](../../services/branchSearch.service.ts#L148) · [Result scorer](../../lib/topSearch.ts#L404)

21. **Two account date-format choices display the same date.** With the English (India) locale, both `dd MMM yyyy` and `MMM dd, yyyy` rendered `04 Nov 2026`. The two options pass the same date fields to `Intl.DateTimeFormat` with different property order. The locale determines display order in both cases. *Reproduced with the application's formatting options.* [Settings choices](../../components/account/PersonalSettings.tsx#L362) · [Formatting options](../../components/settings/UserPreferencesApplier.tsx#L59) · [Formatter](../../components/settings/UserPreferencesApplier.tsx#L138)

22. **A completely failed WhatsApp collections planning run is recorded as partial.** When every claimed branch fails inside the loop, the collections planner finishes with zero completed branches and status `PARTIAL`. The daily-report planner records the equivalent all-failed outcome as `FAILED`. Operators cannot interpret the same job statuses consistently across the two planners. *Source trace.* [Collections planner](../../services/whatsappPlanner.service.ts#L2702) · [Report planner](../../services/whatsappReportPlanner.service.ts#L251)

23. **“Decline invite” leaves the staff invitation pending.** The control navigates to the workspace list. An owner still sees the invitation as active, and the intended recipient can reopen it until it expires or is revoked.
